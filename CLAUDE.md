# CLAUDE.md

Контекст для Claude Code при работе в этом Unity-проекте. Игровой дизайн — в `design-document.md` в корне проекта; этот файл — про то, как устроен код и как здесь принято работать, а не про то, какая это игра по замыслу.

## Проект

Unity 6000.3.23f1, 2D, карточный рогалик. Весь интерфейс — Canvas/uGUI (не мировые спрайты, не UI Toolkit). Input — новая Input System (`Mouse.current`), клики по UI — через `IPointerClickHandler`, не через `Physics2D.OverlapPoint`.

**Текущий статус:** боевое ядро (бой одного забега) реализовано и прогнано целиком — виртуальный секундомер, карты, три статус-эффекта из первой волны плюс четыре из второй, колода/рука на 7 слотов, конец боя, динамический спавн одного или нескольких врагов. Хаб, карта мира, персонажи кроме базового — не начаты.

## Архитектура

- **`CombatManager`** — виртуальный секундомер (`CurrentTime`), реестр `IScheduledEvent`, резолвер (`ResolveUpTo`). Держит прямые ссылки только на участников боя (`Player`, `List<Enemy>`, регистрируются кодом спавнера, не через инспектор) — карты, колода и рука сюда никогда не входят, это отдельные менеджеры.
- **`Card` / `CardData` / `CardInstance`** — `CardData` (`ScriptableObject`) — общий шаблон-ассет одной уникальной карты (например, один `Jab_Data` на все копии Тычка в игре). `CardInstance` — конкретная копия в колоде персонажа: ссылка на `CardData` + личные добавки поверх шаблона (например, только у одной копии карты выставлено «Сжигаемое», остальные копии той же карты — нет). `Card` (`MonoBehaviour` на игровом объекте) хранит `CardInstance`, не сырой `CardData` — `data` на нём просто read-only проброс к `instance.data`.
- **Эффекты карты (и теперь — шагов поведения врага) — три раздельных списка, не один полиморфный список.**
  - `instantActions: List<InstantActionEntry>` — разовые механические действия (Урон/Блок/Лечение), одинаковая форма `kind` + `amount` + `hitCount` (сколько раз ударить/дать блок/вылечить за один розыгрыш — каждое повторение пересчитывает модификаторы заново, не один раз на сумму). `Apply()` принимает явные `source` (кто действует) и `target` (кто получает) — Урон считается через `source.CalculateOutgoingDamage()` → `target.ApplyIncomingDamageModifiers()` → `target.TakeDamage()`; Блок и Лечение получает `target ?? source` (то есть по умолчанию себе, если цель не задана — так у карт игрока с Блоком, где цели нет вообще, — но реальной цели, если она передана, как у шагов паттерна врага, дающих блок союзнику).
  - `appliedEffects: List<AppliedEffectEntry>` — наложение статус-эффекта, форма `statusType` + `stacks` (`float`, не `int` — см. ниже про Пошатывание).
  - `properties: CardPropertyFlags` — `[Flags] enum` (Сжигаемое, Впереди…), комбинируются побитово, не список объектов. (Только у карт, не у шагов паттерна врага.)
  - `drawCardsOnPlay: int` — отдельное поле на `CardData`, не третий тип действия: у него нет общей формы ни с одним из списков выше.
  - Причина именно такого разделения (не полиморфизм через `[SerializeReference]`): Unity не даёт inspector-picker для полиморфных списков без стороннего пакета или кастомного `PropertyDrawer` — проверено и подтверждено на практике, не теоретическое решение.
- **`EnemyPatternData` / `EnemyActionStep` / `EncounterData`** — паттерны поведения врага и составы боёв тоже данные, не код. `EnemyPatternData` (ScriptableObject) — зацикленный список `EnemyActionStep` (имя для UI-телеграфа, задержка, `EnemyActionTarget`, те же `instantActions`/`appliedEffects`, необязательный `fallback` того же типа). `EncounterData` (ScriptableObject) — список префабов врагов для конкретного боя, читает `EncounterManager`.
  - `EnemyActionTarget`: `Self`/`Player`/`AllOtherEnemies`/`LowestHpOtherEnemy` (по % HP, не по абсолютным очкам)/`SpecificEnemyIndex`. Резолвится через `CombatManager.Enemies` (публичный `IReadOnlyList<Enemy>`).
  - Если цель шага не находится (мертва/не существует) — используется `fallback` (шаг того же типа); если `fallback` тоже не задан или тоже не находит цель — шаг молча пропускается. Мёртвый исполнитель (`CurrentHP <= 0`) пропускает свой шаг целиком, ещё до попытки найти цель.
  - При смерти любого `Combatant` вызывается `ClearAllScheduledEvents()` — снимает все его тикающие статус-эффекты (через `Dictionary<StatusEffectType, PeriodicEffectEvent> activeScheduledEffects`, не просто `HashSet`-флаг — нужна ссылка на сам объект, чтобы было что отменить в `CombatManager.UnregisterScheduledEvent()`). Собственное расписание врага (`IScheduledEvent` на нём самом) снимается симметрично, но из `EncounterManager` (кто регистрирует — тот и отписывает), не изнутри `Combatant`.
  - `Block`/`CurrentBlock`/поглощение урона блоком — на базовом `Combatant`, не только на `Player` (`Player.cs` теперь пустой класс без переопределений): раз враги тоже могут получать блок через паттерн, это больше не свойство одной стороны.
- **`DeckManager`** — колоды персонажа/добора/сброса/сжигания. Перемешивание, приоритет «Впереди» при сборке колоды добора на старте боя.
- **`HandManager`** — рука на 7 **явных** слотах (`RectTransform[7]`, не `Horizontal Layout Group`) — осознанный выбор автора, не пропущенная оптимизация. Сдвиг влево при уходе карты — ручной перебор массива, не автолэйаут.
- **`TargetSelectionManager`** — единственная точка входа для клика по картам/целям. И `Card`, и `Combatant` реализуют `IPointerClickHandler`, оба зовут сюда (`SelectCard`/`SelectTarget`). Здесь же — блокировка ввода после конца боя (`LockInput`).
- **`Combatant`** (abstract, база для `Player`/`Enemy`) — HP, стаки эффектов (`Dictionary<StatusEffectType, float>` — намеренно `float`, не `int`: Пошатывание может нести дробное значение секунд), расчёт исходящего урона (Сила/Слабость), входящих модификаторов урона (Уязвимость) и получаемого блока (Крепкость/Хрупкость).
- **`EncounterManager`** — динамический спавн врагов из `List<GameObject>` префабов при старте боя, поддерживает одного или нескольких. Каждый `EnemyPrefab` несёт свой HP-бар, таймер атаки и индикатор стаков эффектов как дочерние объекты, уже подключённые друг к другу и к себе внутри самого префаба — спавн отдельно не донастраивает UI, только `combatManager`/`player`-ссылки, которые не являются частью префаба.
- **`IScheduledEvent`/`OneShotEvent`/`PeriodicEffectEvent`** — всё, что происходит в конкретный момент виртуального времени (атака врага, эффект карты, тик статус-эффекта), живёт в одном реестре с единым правилом ничьей (точное совпадение времени → побеждает карта игрока, `Priority` на интерфейсе).
- **Пошатывание — не через общий `Dictionary` стаков.** Это не столько статус-эффект, сколько мгновенное действие над `Enemy.scheduledHitTime`: применяется сразу целиком, а не тикает через `StatusEffectRules`. Отображается в UI отдельным полем `Enemy.StaggerDisplay`, не через `GetStacks`.

## Принципы, которых придерживались

- **KISS.** Несколько раз откатывались от «более правильного» ООП к более простому: полиморфные подклассы эффектов через `[SerializeReference]` заменены на плоские списки с `enum`-переключателем, когда выяснилось, что инспектор не даёт нормальный picker типов. Подклассы `AttackCard`/`SkillCard`/`PowerCard` заменены на один `Card` + список эффектов-данных.
- **YAGNI.** Механика отката времени, экран колоды, передача тега «Впереди», архитектура под мультиплеер и под несколько играбельных персонажей — продуманы на словах ровно настолько, чтобы не запереть себя архитектурно, но не реализуются, пока не понадобятся по-настоящему.
- **Разделение по владению, не по формальному типу.** `CombatManager` знает только про участников боя — карты/колода/рука никогда не сливаются в него, даже когда это означает больше файлов. При этом менеджер без своего состояния (`CombatEndManager`) слился обратно в `CombatManager`, когда стало ясно, что разделение не окупается для чего-то настолько маленького.
- **Данные отдельно от поведения.** Карты, эффекты, свойства карт — сериализуемые данные, а не иерархии классов с зашитым поведением.
- **Проверка перед доверием.** Не полагаться на память о поведении Unity API без проверки — конкретно наступили на утверждение про `[SerializeReference]`-picker, оказавшееся неверным, и задокументировали настоящее поведение после проверки.
- **Один шаг — одна проверка.** Каждое изменение проверяется в Play Mode (часто через `[ContextMenu(...)]`-кнопки для функционала без готового UI) до перехода к следующему шагу.

## Известные грабли

- Компонент, заспавненный через `Instantiate(prefab, parent)`, уже прошёл `Awake()` к моменту, когда код после `Instantiate()` успевает проставить его публичные поля — код внутри `Awake()`, читающий эти поля, получит `null`/значение по умолчанию. Наступали дважды: `Card.nameLabel` (сейчас `Awake()` проверяет `instance != null && instance.data != null`), самостоятельная регистрация `Enemy` в `CombatManager` (перенесена наружу, в `EncounterManager`).
- `RectTransform` с `Rotation Y = 180°` (частый способ горизонтально отзеркалить спрайт) ломает попадание клика через `IPointerClickHandler`/`GraphicRaycaster`. Зеркалить нужно отрицательным `Scale X`, не поворотом по Y.
- При переносе `.cs`-файлов между папками в обход самой Unity (файловый менеджер, внешний агент) рвётся привязка `.meta`-GUID → компонент становится «Missing Script» на сценах/префабах, где он уже использовался. Переносить файлы стоит либо через Project-окно Unity, либо при закрытом редакторе с последующим полным переоткрытием проекта.
- При правке одного и того же класса по частям в нескольких сообщениях легко случайно продублировать объявление класса в двух файлах сразу (`CS0101`). Держать один класс — один файл, где это возможно.
- При обобщении действия с одного жёстко зашитого получателя (`combatManager.player`) на явный параметр — легко забыть один из веток `switch` и оставить её всё ещё жёстко привязанной к старому получателю (`Block` какое-то время начислялся всегда `source`, `target` игнорировался). Тест, который путает `source` и `target` в один и тот же объект (цель = сам исполнитель), не может поймать эту ошибку — числа совпадут что с багом, что без него. Проверять подобные правки нужно сценарием, где источник и цель — заведомо разные `Combatant`, и сверять значение у **каждого** конкретного получателя по отдельности, а не факт "что-то изменилось".
