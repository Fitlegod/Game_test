## Виртуальный секундомер: `CombatManager`

Весь бой существует во времени одного `int CurrentTime` (целые секунды), а не в реальном времени кадров. Время не течёт само по себе — оно **прыгает вперёд ровно тогда, когда игрок играет карту**: `Card.Play()` вызывает `combatManager.AdvanceTime(data.timeCostSeconds)`. Больше ничего в проекте не двигает `CurrentTime`. Всё остальное (таймер атаки врага, тики эффектов, UI-обновления) просто читает текущее значение или ждёт, пока секундомер до него доберётся.

Поля и обязанности:
- `CurrentTime { get; private set; }` (`int`) — сам секундомер, наружу только для чтения. Единственное место, где он уменьшается, — `Rewind` (см. раздел «Откат»).
- `EffectTime` — момент, в который «происходит» эффект: `CurrentEvent != null ? CurrentEventTime : CurrentTime`. Эффект внутри события (карта, ход врага, тик) считается в момент события, а не в `CurrentTime` — тот к моменту срабатывания может уже стоять в конце каста. От `EffectTime` отсчитываются первый тик статус-эффекта (`Combatant.AddEffectStacks`) и Оглушение (`Enemy.ApplyStun`); остальные места с `CurrentTime` (`Card.Play`, `ScheduleFirstAction`, `HandManager.BeginNewHand`, телеграф) намеренно читают именно текущее время.
- `ReplayUntil` (`int`, `-1` — отката не было) — до какого момента действия врагов не бьют по игроку после отката; сбрасывается в `ResetForNewCombat`.
- `ScheduledEvents` и `Journal` — публичные виды только для чтения на список событий и журнал обратных процедур (нужны тестам и отладке).
- `Enemies` (`IReadOnlyList<Enemy>`) — публичный вид на приватный `List<Enemy> enemies`; заполняется один раз через `RegisterEnemies(List<Enemy>)`, которую вызывает `EncounterManager` после спавна. Заодно подписывает `HandleEnemyDeath` на `OnDeath` каждого врага.
- `player` — публичное поле `Player`, но с динамическим спавном игрока (см. [enemies.md](enemies.md) про `EncounterManager`) в инспекторе больше не выставляется — присваивается только через `SetPlayer(newPlayer)`, вызываемую `EncounterManager` сразу после `Instantiate` игрока на каждый новый бой.
- `scheduledEvents` (`List<IScheduledEvent>`) — плоский список, не куча/приоритетная очередь. `ResolveUpTo` каждый шаг цикла линейно сканирует весь список заново — O(n) на срабатывание, но при масштабе «несколько врагов + несколько активных эффектов за один бой» это осознанно достаточно просто (YAGNI), а не недосмотр.
- `RegisterScheduledEvent`/`UnregisterScheduledEvent` — используются: `Card.Play` (разовый `OneShotEvent` эффекта карты), `Combatant.AddEffectStacks` (периодический тик статус-эффекта), `HandManager.BeginNewHand` (периодический автодобор, регистрируется заново на каждый бой — см. [deck-hand.md](deck-hand.md)), `EncounterManager` (регистрирует сам `Enemy`, потому что `Enemy` — это `IScheduledEvent`).

### `StateVersion` — версия состояния для UI-кэша

`CombatManager.StateVersion` (`int`) растёт при любом изменении состояния боя: каждая `Record` (в начале, до раннего выхода — то есть и для изменений вне событий), `AdvanceTime`, конец `Rewind` (обратные процедуры меняют состояние в обход `Record`), `ResetForNewCombat` и `Touch()` (его зовёт `Combatant.SetCurrentHP`, меняющий HP мимо журнала). UI (`CombatantStatusDisplay`, `Card.UpdateEffectText`) пересобирает строки только при смене версии. **Правило:** новое изменение состояния, видимого игроку, должно идти через `Record` или вызывать `Touch()`, иначе текст не обновится (тест `V1`).

### `AdvanceTime` и `ResolveUpTo`

- `AdvanceTime(int amount)` — `CurrentTime += amount`, затем обновляет текстовый UI «Прошло времени». Вызывается только из `Card.Play` с `timeCostSeconds` сыгранной карты.
- `ResolveUpTo()` — резолвер, **без параметра**: на каждом шаге цикла заново читает `CurrentTime` (откат может уменьшить его прямо посреди разбора — остаток каста карты Отката проживается уже после переноса). Пока среди `scheduledEvents` есть события с `IsPending && NextTime <= CurrentTime`, находит **одно** с наименьшим `NextTime` (при равенстве — по правилу ничьей ниже), выставляет `CurrentEvent`/`CurrentEventTime` (нужны журналу), вызывает его `Trigger()`, и повторяет проверку заново с нуля. Поскольку `Trigger()` какого-то события может зарегистрировать новое событие (например, второй тик периодического эффекта), следующий проход цикла увидит и его — резолвер не работает со снимком списка, а перечитывает его каждую итерацию. В начале каждой итерации цикла проверяется `combatOver`: если бой окончен (победа или поражение), разбор прекращается и следующее событие не выбирается (ГДД §4.2). Событие, внутри которого бой закончился, дорабатывает до конца (остальные цели той же карты или шага), но события, запланированные позже — тики, добор, действия врагов, Откат — уже не срабатывают.
- **Правило ничьей** (дизайн-документ §4.1; `EffectiveKey` в `CombatManager`): порядок задаёт **один ключ** на событие — кортеж, который сравнивается по полям по очереди; `ResolveUpTo` берёт среди готовых событий (`NextTime <= CurrentTime`) то, у которого ключ наименьший. Парных правил нет, поэтому порядок всегда линейный и не зависит от порядка в списке `scheduledEvents`. Поля ключа по порядку:
  1. `NextTime` — момент;
  2. окружение: `0` — нет, `1` — группа 2 (затухание блока всегда в конце момента, сильнее правила повтора);
  3. повтор: `0` — повторяемое после отката (`ReplayOrderOf > 0`), `1` — нет (повторяемые идут раньше новых);
  4. номер прежнего срабатывания (для повторяемых, иначе `0`; см. `ReplayOrder` ниже);
  5. группа (`EventGroup`): `Player = 0`, `Enemies = 1`, `Environment = 2` — константы в `Combat/TimedEffects.cs`;
  6. носитель: индекс в `Enemies` (слева направо; носитель — сам `Enemy` или `Owner` тика) для группы врагов, иначе `0`;
  7. номер создания;
  8. признак «Регенерация»: `0` у тика Регенерации, `1` у остальных.
  - **Эффективный ключ Регенерации.** Для тика «лечит по времени» (`StatusEffectRules.IsHealOverTime`, сейчас Регенерация) ключ = минимум из его базового ключа и базовых ключей ожидающих тиков «бьёт по времени» (`StatusEffectRules.IsDamageOverTime`: Отравление, Кровотечение) **того же бойца с тем же `NextTime`**, а последнее поле — `0`. Так Регенерация встаёт прямо перед тем тиком, чьё место заняла. Если у бойца в этот момент нет Отравления или Кровотечения, Регенерация стоит на своём обычном месте. Пример (один враг, один момент): R — Регенерация, наложенная врагом на себя (группа 1); P — Отравление от игрока (группа 0); A — действие этого врага (группа 1, создано раньше R). Базовый порядок по парам дал бы круг R<P (Регенерация), P<A (группа 0), A<R (создание); по ключу R получает ключ P и идёт перед ним: R, P, A при любом порядке регистрации и после отката.
  - Группа 0: карты (`OneShotEvent`, `priority: EventGroup.Player`), таймер добора, тики эффектов на игроке (кто бы ни наложил) и тики, которые наложил игрок (в том числе на врагов). Группа 2: тики затухания блока (`isEnvironment`). Группа 1: `Enemy` (его действия) и тики, которые наложил на врага враг или неизвестно кто (`PeriodicEffectEvent.Priority`, см. `Applier` в effects.md).
  - Номер создания — сквозной счётчик `creationOrders` в `CombatManager`: выдаётся в `RegisterScheduledEvent`, только если у события ещё нет номера (повторная регистрация обратной процедурой номер не меняет); сбрасывается в `ResetForNewCombat`. Периодический эффект создан в момент наложения (когда создан его `PeriodicEffectEvent`).
  - Следствие: Слабость, наложенная картой на врага в тот же момент, когда он атакует, ослабляет эту атаку.

### Конец боя, смена боёв и `PlayerRunState`

- `Start()` — с динамическим спавном игрока (`EncounterManager` появляется позже самого `CombatManager`) здесь больше нет подписки на `player.OnDeath`: она невозможна на старте сцены, игрока ещё не существует. Остаётся только `UpdateBudgetText()` и очистка `combatResultText`.
- `SetPlayer(newPlayer)` — единственное место, где присваивается поле `player` и подписывается `HandlePlayerDeath` на его `OnDeath`. Повторный вызов сначала снимает подписку с прежнего игрока, поэтому обработчик никогда не висит на одном игроке дважды (`OnDefeat` не сработает дважды). Вызывается **после** `ResetForNewCombat` (сброс очищает расписание и список бойцов с тиком затухания) `EncounterManager`-ом сразу после спавна игрока на **каждый** бой (не только на первый) — старая подписка на прошлого (уже уничтоженного) игрока при этом просто перестаёт существовать вместе с ним, пересоздавать её вручную не нужно.
- `ResetForNewCombat()` — сброс между боями: чистит `scheduledEvents` (расписание прошлого боя целиком — старые `OneShotEvent`/`PeriodicEffectEvent`/`Enemy` не должны тикать во время следующего), обнуляет `CurrentTime`, снимает флаг `combatOver`, чистит список `enemies`, обновляет текст времени, **очищает `combatResultText`** и **разблокирует ввод** через `TargetSelectionManager.Instance.UnlockInput()`. Очистка текста и разблокировка обязательны по одной и той же причине: `EndCombat` выставляет их (текст результата и блокировку) без собственного таймера или условия снятия, поэтому без симметричного сброса здесь оба состояния прошлого боя — «Победа»/«Поражение» на экране и замороженный клик — просто утекли бы в начавшийся новый бой.
- `HandlePlayerDeath()` — подписан на `player.OnDeath` (через `SetPlayer`): `EndCombat("combat.defeat")` (ключ строки «Поражение»), затем поднимает `OnDefeat`. Следующий бой сам не стартует — `EncounterManager.HandleDefeat` возвращает игрока на карту (см. [enemies.md](enemies.md), [map.md](map.md)). Начинается с `if (combatOver) return;`, как и `HandleEnemyDeath`: смерть игрока после победы второго исхода (`OnDefeat`) не поднимает.
- `HandleEnemyDeath()` — подписан на `OnDeath` каждого врага. `RegisterEnemies` перед подпиской снимает прежнюю (и со старого списка, и с самого врага), поэтому повторная регистрация не удваивает вызовы. Сначала `if (combatOver) return;` — если бой уже закончен (например, поражением), второго исхода не будет. Завершает бой победой, только когда **все** враги имеют `CurrentHP <= 0` (`enemies.TrueForAll(...)`) — гибель одного врага при живых остальных бой не прерывает. При победе, помимо `EndCombat("combat.victory")` (ключ строки «Победа»), поднимает `OnVictory` — на него подписан `EncounterManager.HandleVictory`.
- `event Action OnVictory` / `event Action OnDefeat` — по одному событию на исход боя; обе подписки держит `EncounterManager`. `OnDeath` на `Combatant` общий для обеих сторон, эти два — уже итог боя.
- `EndCombat(message)` — идемпотентен (флаг `combatOver`, второй вызов — no-op), выставляет текст результата и вызывает `TargetSelectionManager.Instance.LockInput()`, замораживая ввод.

**`PlayerRunState`** (`Combat/PlayerRunState.cs`) — не MonoBehaviour, просто `public static class` с одним полем `public static int? PersistedHP`. Хранит HP игрока между боями одного забега: `EncounterManager.HandleVictory` записывает в него `currentPlayer.CurrentHP` перед уничтожением старого игрока, `EncounterManager.SpawnPlayer` читает его и накатывает через `Combatant.SetCurrentHP` на свежезаспавненного игрока следующего боя, если значение задано (`HasValue`). `null` означает «полное здоровье»: так начинается забег (`MapManager.Start` явно ставит `null`, чтобы статика не пережила перезапуск Play Mode без перезагрузки домена) и так же сбрасывается при поражении (`EncounterManager.HandleDefeat`). Поскольку это статическое поле, а не часть сцены, оно переживает `ResetForNewCombat()` и всё, что происходит внутри одного забега.

## Расписание: `IScheduledEvent` / `OneShotEvent` / `PeriodicEffectEvent`

`IScheduledEvent` — интерфейс с четырьмя членами: `NextTime` (`int`, когда сработать), `Priority` (тай-брейк, меньше — раньше), `IsPending` (ждёт ли событие срабатывания) и `Trigger()` (само действие). «Бесконечного времени» в проекте нет: отработавшее событие не получает `NextTime = ∞` и не удаляется из списка, оно просто `IsPending == false`, и резолвер его пропускает. Удаляются события только в `ResetForNewCombat` и через `Unregister` (смерть носителя) — поэтому откат может вернуть событие «в ожидание». Всё, что происходит в конкретный момент виртуального времени, живёт в одном реестре `CombatManager.scheduledEvents` через этот интерфейс — атака врага, разовый эффект карты, тик статус-эффекта не различаются резолвером, только своей реализацией `Trigger()`.

- **`OneShotEvent`** — одноразовое событие (конструктор: `CombatManager`, время, `Priority` — карты всегда `0`, действие с флагом повтора). `Trigger()` ставит `fired = true`, **не трогает `NextTime`**, пишет в журнал `Rearm(true)` и вызывает действие с `IsReplay`. `IsPending => !fired`. `Rearm(bool replay)` возвращает событие в ожидание (используется откатом) и выставляет `IsReplay`.
- **`PeriodicEffectEvent`** — интервальное повторение (`int` `startTime`, `interval`, `NextTime`): каждый `Trigger()` вызывает `onTrigger()`, затем `NextTime += interval`; `IsPending` всегда `true`. Необязательный флаг конструктора `isEnvironment` (по умолчанию `false`) даёт `Priority = 2`. Необязательный `Owner` (`Combatant` передаёт `this`, таймер добора — `null`); если `Owner` задан, `Trigger()` пишет в журнал `NextTime -= interval`. `Shift(delta)` двигает `NextTime` (используется откатом для событий стороны игрока). Тикает, пока его явно не отпишут через `UnregisterScheduledEvent` — это делает `Combatant.ClearAllScheduledEvents()` при смерти носителя (см. [effects.md](effects.md)); автодобор `HandManager` не отписывается до конца боя.
- **`Enemy` сам реализует `IScheduledEvent` напрямую** (не через `PeriodicEffectEvent`) — его `Trigger()` и `IsPending` разбираются в [enemies.md](enemies.md). `Enemy.IsPending => CurrentHP > 0 && паттерн не пуст`: пустой паттерн по-прежнему даёт `Debug.LogError`, но время врага в бесконечность не ставится — он просто не `IsPending`. Регистрирует/отписывает его `EncounterManager` (кто заспавнил — тот и владеет подпиской), а не сам `Combatant`/`Enemy` — симметрично тому, как `ClearAllScheduledEvents` работает только с собственными тикающими эффектами носителя.

## Откат («Откат N») и журнал обратных процедур

Карта с действием `InstantActionKind.Rewind` (`amount = N`, `hitCount` игнорируется) вызывает `CombatManager.Rewind(N)` изнутри своего `OneShotEvent`. Снимков состояния нет — откат делается только **обратными процедурами** из журнала.

**Правила.** Эффект карты срабатывает в момент `T` (`NextTime` её события). `R = max(0, T − N)`, `S = T − R`; если `S == 0` — ничего не происходит.
- Игрок не меняется: HP, блок, эффекты, рука, колоды остаются как есть.
- Всё, что события сделали с врагами и мировыми событиями в моменты `>= R`, отменяется. Убитый в интервале враг оживает вместе со своими событиями; тики, созданные в интервале, исчезают.
- Каждое `OneShotEvent` карты, сработавшее в моменты `>= R` (кроме самой карты Отката), снова в ожидании с `IsReplay = true`. Его прошлый эффект на врагов уже отменён, так что при повторе он сработает ровно один раз. При `IsReplay` эффект **не действует на игрока** (цели-Player, добор, сам Откат), на врагов действует (`Card.ApplyAllEffects`).
- `ReplayUntil = max(ReplayUntil, T)`: действие врага с моментом `<= ReplayUntil` не действует на игрока (цель `Player` пропускается), на других врагов действует.
- `CurrentTime −= S`; `ResolveUpTo` продолжает разбор до нового времени.
- Ещё не сработавшие `OneShotEvent` (`NextTime > T`) не трогаются.

**Стороны событий.** «Мировое» — объект `Enemy` или `PeriodicEffectEvent` с `Owner is Enemy`. «Сторона игрока» — всё остальное: таймер добора (`Owner == null`), периодические эффекты на игроке, `OneShotEvent` карт. Откат события стороны игрока никогда не удаляет из списка. Периодические события стороны игрока сдвигаются `NextTime −= S`; инвариант: `(NextTime − T)` до отката равно `(NextTime − R)` после. Пример: время 8, добор в 8 (следующий 10), «Откат 3» с cost 1, delay 1 → `T=9, R=6, S=3`, следующий добор в 7.

**Журнал.** `List<UndoEntry> journal`, `UndoEntry { Time; Target; Source; Undo }` (класс в `CombatManager.cs`). `CombatManager.Record(target, undo)` пишет запись, только если идёт событие (`CurrentEvent != null`) и не идёт откат (`isRewinding`): вне событий (спавн, начало боя) ничего не пишется. `Time` — момент события (`CurrentEventTime`), `Source` — само событие. Обратная процедура хранит реальную разницу, а не входное число. Что пишется:
- `TakeDamage` — реально снятые блок и HP; `Heal` — реально вылеченное (с учётом `maxHP`); `GainBlock` — добавленный блок; `AddEffectStacks`/`RemoveStacks` — реальная разница стаков (с учётом нуля); созданное периодическое событие — удаление его из `activeScheduledEffects`; смерть (`ClearAllScheduledEvents`) — возврат снятых записей в `activeScheduledEffects`.
- `RegisterScheduledEvent`/`UnregisterScheduledEvent` (только для мировых событий) пишут обратное действие сами — поэтому смерть врага и создание тиков отменяются без правок `EncounterManager`. `Unregister` запоминает индекс события в списке, и обратная процедура вставляет его **на прежнее место** (`Insert`, с ограничением по длине списка), а не в конец.
- `OneShotEvent.Trigger` — `Rearm(true)`; `PeriodicEffectEvent.Trigger` (с `Owner`) — `NextTime −= interval`; `Enemy.Trigger` — прежние `currentStepIndex` и `nextActionTime`; `Enemy.ApplyStun` — прежние `nextActionTime` и поля Оглушения.
- `Target` записи — тот, чьё состояние меняется (владелец события; `null` для таймера добора и карт).

**`Rewind(n)`** идёт по журналу с конца и вызывает `Undo` для записей с `Time >= R`, **кроме**: `Target is Player`; `Source` — периодическое событие стороны игрока; `Source` — событие самой карты Отката. Затем удаляет из журнала все записи с `Time >= R`, сдвигает периодические события стороны игрока на `−S`, уменьшает `CurrentTime`, обновляет `ReplayUntil` и текст времени. Во время `Undo` `Record` ничего не пишет. Если бой уже окончен (`combatOver`), `Rewind` ничего не делает: откат возможен только во время боя (ГДД §8.2), враги не оживают после победы.

**Порядок повтора (`ReplayOrder`).** Карта регистрируется при розыгрыше, поэтому в первом прохождении она могла сработать *после* врага того же момента. Чтобы повтор не менял такой порядок, `ResolveUpTo` нумерует срабатывания сквозным счётчиком `fireCounter` (сбрасывается в `ResetForNewCombat`, при откате не уменьшается); номер срабатывания пишется в `UndoEntry.FireOrder`. Обратная процедура срабатывания (`OneShotEvent`, `PeriodicEffectEvent` с `Owner`, `Enemy.Trigger`) кладёт номер прежнего срабатывания в стек события (`CombatManager.PushReplayOrder`; откат идёт от новых записей к старым, поэтому сверху лежит самое раннее). «`ReplayOrder` события» — вершина его стека, `0` — не повтор; при срабатывании `ResolveUpTo` снимает вершину. Стек, а не одно число, потому что враг может ходить в откатываемом интервале несколько раз и каждый ход надо повторить на своём месте. Номер повтора действует **только для событий с `NextTime <= ReplayUntil`** (интервал повтора): `ReplayOrderOf` для остальных возвращает `0`. Когда `ResolveUpTo` выбирает событие с `NextTime > ReplayUntil`, все стеки номеров очищаются: если при повторе событие сработало меньше раз, чем в первом проходе (например, новая карта оглушила врага и его ход ушёл позже), «залипший» номер не даёт ему обгонять новые события одного момента вне интервала. Выбор при равном `NextTime`: у обоих `ReplayOrder > 0` — меньший первым; только у одного — он первым (повторяемое раньше новой карты); иначе — по правилу ничьей выше (группа, номер создания / носитель слева направо).

**Откат в карте — один раз и последним.** `Card.ApplyAllEffects` выполняет действие `Rewind` ровно один раз на карту (первое из списка; число целей и `targetTag` не важны) и **после** всех остальных действий, эффектов и добора. Поэтому у карты Отката нет записей журнала, сделанных уже после переноса времени. Урон такой же карты (`[Rewind, Damage]`) остаётся: записи её события (`Source == self`) Откат пропускает, а затем вычёркивает из журнала все записи с `Time >= R`, так что последующий Откат их уже не отменит и карта не переигрывается — согласуется с правилом «карта Отката не переигрывает саму себя».

**Тики, отменённые откатом, при повторе переиспользуются.** Обратная процедура создания тика (`AddEffectStacks`) убирает его из расписания и кладёт в `Combatant.undoneTicks[type]`. Если при повторе тот же носитель получает тот же тип эффекта от того же источника (`Applier`) в момент не позже `ReplayUntil`, `AddEffectStacks` возвращает прежний объект (`Restart(EffectTime)`) вместо нового: он сохраняет номер создания и стек номеров повтора, поэтому в своём моменте встаёт на то же место, что и в первом проходе (например, тик Уязвимости остаётся раньше карты с уроном). Другой источник или момент позже `ReplayUntil` — новый объект с новым номером создания, устаревшая запись `undoneTicks` удаляется.

**Защита.** Откат применяется только из `OneShotEvent` карты игрока. Если `Rewind` вызван из действия врага (или из тика), ничего не происходит, в Console — `Debug.LogError` с именем врага.

**Повтор с параметрами первого раза.** `Card.Play` создаёт для карты `memo` — словарь «(номер действия, цель) → `float`». Первое срабатывание записывает туда «исходящее» число каждого `InstantActionEntry` (`Apply` возвращает `float`): урон после Силы/Слабости (до модификаторов цели, **без округления** — иначе при повторе вышло бы двойное округление), блок после Крепости/Хрупкости получателя, лечение. Срабатывание с `IsReplay` передаёт запомненное число в `Apply(..., outgoingOverride)` для целей-врагов: формулы источника не пересчитываются по текущему состоянию игрока (игрок при откате не откатывается, поэтому Сила, полученная в интервале, иначе увеличила бы повторный удар). Модификаторы цели (Уязвимость, блок врага) применяются как при обычном ударе — они берутся с врага, который уже откачен. Эффекты-стаки (`AppliedEffectEntry`) — фиксированные числа, в `memo` не нужны. Повтор `memo` не перезаписывает, так что и второй откат использует числа первого прохода.

Победа/поражение, объявленные внутри откатываемого интервала, журналом не отменяются.

## События для триггеров

`CombatManager` (A9) — C#-события для талантов, реликвий, проклятий и стихий (подписчиков в игре пока нет, только тесты W):

| Событие | Кто вызывает и когда |
|---|---|
| `OnCombatStart()` | `EncounterManager.StartEncounter` в конце настройки: после `SetPlayer`, `RegisterEnemies` и начальной руки, до первого хода |
| `OnCardPlayed(CardInstance, Combatant target)` | `Card.Play` до `AdvanceTime` |
| `OnCastSeconds(int seconds)` | `Card.Play` после `AdvanceTime(timeCostSeconds)`, до `ResolveUpTo` |
| `OnParry(CardInstance card, Enemy enemy, bool isReplay)` | `Card.ApplyAllEffects` один раз на срабатывание карты, когда выполнено условие Парирования, после обычных эффектов и до `parryActions`/`parryEffects` (см. [cards.md](cards.md)); `enemy` — парированный враг (первый по `Enemies`, если подходят несколько); `isReplay` — как у `OnAttack`. Вызывается внутри события карты, поэтому правила `OnAttack` (журнал, откат, повтор) действуют и здесь |
| `OnAttack(source, target, damage, isReplay)` | `InstantActionEntry.Apply` (Damage) после каждого реально нанесённого удара (после `TakeDamage`), для обеих сторон; `damage` — итоговый урон после модификаторов; удар по уже мёртвой цели и пропущенные при повторе удары (действие врага по игроку, пропуск цели при повторе карты) события не дают. `isReplay = CurrentEventTime <= ReplayUntil` |

Вызывает событие через `RaiseCombatStart/RaiseCardPlayed/RaiseCastSeconds/RaiseParry/RaiseAttack` (C#-событие нельзя вызвать снаружи класса).

Правила:
- `OnCombatStart`, `OnCardPlayed`, `OnCastSeconds` вызываются **вне событий таймлайна**. Журнал их не пишет, после отката они не повторяются: это действия игрока, а игрок не откатывается.
- `OnAttack` вызывается **внутри события**. Подписчик пишет изменения своего состояния (счётчики) через `combatManager.Record(null, undo)`; изменения врагов идут обычными методами `Combatant` (они уже пишутся в журнал). При откате всё это отменяется, при повторе атака снова вызывает `OnAttack`, и реакция срабатывает заново.
- При `isReplay == true` подписчик не применяет эффекты к игроку (как карта при повторе).
- «Подождать» и Оглушение `OnCastSeconds` не вызывают.

## «Подождать»

`CombatManager.Wait()`: если бой окончен — ничего; иначе `AdvanceTime(1)` и `ResolveUpTo()`; секундами каста не считается. Единая точка входа для ввода — `TargetSelectionManager.Wait()` (поле `combatManager` задано в сцене): игнорирует вызов при `LockInput` и пока `PendingCard != null`. Её зовут `CombatHotkeys` (Пробел, только на экране боя) и кнопка «Подождать» (см. [ui.md](ui.md)).

## Единая точка кликов: `TargetSelectionManager`

Синглтон (`Instance`, выставляется в `Awake`). И `Card`, и `Combatant` реализуют `IPointerClickHandler`, но оба **не** обрабатывают клик сами — оба сразу зовут сюда (`SelectCard`/`SelectTarget`).

- `PendingCard` — какая карта сейчас ждёт клика по цели (или `null`).
- `HoveredTarget` — над каким `Combatant` сейчас курсор; используется только для живого предпросмотра урона/блока в тексте карты (см. [cards.md](cards.md)), к выбору цели отношения не имеет.
- `SelectCard(card)` — если `card.RequiresTarget` (есть хоть одно действие/эффект с `EffectTargetTag.Enemy`), карта становится `PendingCard` и ждёт клика по цели; иначе разыгрывается немедленно с `target: null`.
- `SelectTarget(target)` — срабатывает только если есть `PendingCard` и `PendingCard.IsValidTarget(target)` (сейчас — `target is Enemy`); разыгрывает карту по цели и сбрасывает `PendingCard`.
- `LockInput()` — выставляет `inputLocked`, проверяется в начале и `SelectCard`, и `SelectTarget`. Единственный способ, которым `CombatManager.EndCombat` замораживает ввод после конца боя.
- `UnlockInput()` — снимает `inputLocked`. Единственный вызывающий — `CombatManager.ResetForNewCombat()` в начале следующего боя; без него `inputLocked`, однажды выставленный `LockInput()`, не снимался бы вообще ничем, и после первой же победы весь дальнейший цикл боёв оставался бы некликабельным.
- `SetHoveredTarget`/`ClearHoveredTarget` — вызываются из `Combatant.OnPointerEnter`/`OnPointerExit`, чисто для наведения, к блокировке ввода не относятся.

## `Combatant` — участник боя (структура)

Абстрактная база `Player`/`Enemy`. Здесь описана только структурная роль в бою и обработка кликов/смерти; формулы урона/блока/лечения и хранилище стаков — в [effects.md](effects.md).

- `CurrentHP`/`CurrentBlock` — публичные для чтения, `protected`/`private set`. `maxHP` — сериализуемое поле на 30 по умолчанию.
- Реализует `IPointerClickHandler`, `IPointerEnterHandler`, `IPointerExitHandler` — все три сразу пробрасываются в `TargetSelectionManager` (клик → `SelectTarget`, наведение/уход → `SetHoveredTarget`/`ClearHoveredTarget`).
- `event Action OnDeath` — единственный способ, которым внешний код (в первую очередь `CombatManager`) узнаёт о смерти участника; стреляет внутри `TakeDamage` ровно в момент, когда `CurrentHP` впервые достигает `0`. Перед этим вызывается `ClearAllScheduledEvents()` — снимает собственные тикающие статус-эффекты носителя (не его расписание как атакующего — то отдельно, см. выше про `EncounterManager`).
- `Player` — пустой класс без переопределений: игровая сторона игрока целиком собрана из `Combatant` + окружающих менеджеров (`HandManager`, `DeckManager`, `TargetSelectionManager`), ничего специфичного для игрока в самом классе нет.

**UI-потребитель:** `CombatantStatusDisplay` (`UI/CombatantStatusDisplay.cs`) — один компонент на любого `Combatant` (и `Player`, и `Enemy`), объединяющий все четыре прежних отдельных дисплея (`HPBarDisplay`, отдельностоящий Block-индикатор, `EffectStacksDisplay`, `EnemyAttackTimerDisplay`) — они удалены как файлы, их код перенесён сюда буквально. Подробности по каждому куску:
- `hpSlider`/`blockLabel`/`effectsLabel` — те же формулы, что раньше в `HPBarDisplay`/`EffectStacksDisplay`: `Start()` разово ставит `hpSlider.maxValue = target.maxHP`, `Update()` каждый кадр пишет `hpSlider.value = target.CurrentHP` и `blockLabel.text = target.CurrentBlock.ToString()`. `effectsLabel` — точный перенос `BuildEffectsText()` из бывшего `EffectStacksDisplay.Update()`, включая особый случай Оглушения через `enemy.StunDisplay` (см. [effects.md](effects.md)).
- `enemyForTelegraph`/`telegraphLabel`/`combatManager` — заполняются **только** у `EnemyPrefab` (пусто у `PlayerPrefab`, игроку телеграф не нужен); `Update()` пишет в `telegraphLabel` только если `enemyForTelegraph != null`. Логика `BuildTelegraphText()` — точный перенос `EnemyAttackTimerDisplay.Update()` (тот же fallback на «(нет цели)», те же `ComputePreviewAmount` и `CardTextHelpers.HitCountSuffix`, см. [cards.md](cards.md)), см. [enemies.md](enemies.md).
- `combatManager` на этом компоненте нужен исключительно для чтения `CurrentTime` в телеграфе — это не тот `CombatManager`, что на `Combatant`/`Card`, и не часть префаба: `EncounterManager` проставляет его отдельно каждому заспавненному врагу через `GetComponentInChildren<CombatantStatusDisplay>()`, как раньше делал для `EnemyAttackTimerDisplay`.
- Block-индикатор — простой `Image` (квадрат-заглушка, замена на спрайт щита не сделана намеренно, YAGNI) с дочерним `TMP_Text` поверх; отдельным файлом/классом никогда не был, целиком часть `CombatantStatusDisplay` с рождения.
- Сам компонент ничего не пересчитывает — вся математика урона/блока/лечения/статус-эффектов уже применена на `Combatant`/`Enemy` до того, как этот компонент её прочитает (точные формулы — [effects.md](effects.md)); он существует только затем, чтобы игрок видел уже случившийся результат.

**Сверено с кодом:** события `OnVictory`/`OnDefeat`, `HandlePlayerDeath` → `EndCombat` → `OnDefeat`, защита от двойного исхода `if (combatOver) return;`, правило ничьей (`EffectiveKey`), `Rewind` и `Record` — всё в `Managers/CombatManager.cs`.

**Тики затухания блока.** Защита от дублей: `CombatManager` хранит `decayRegistered` (у кого тик уже есть; сбрасывается в `ResetForNewCombat`), поэтому повторный `SetPlayer` или `RegisterEnemies` без сброса второго тика не создаёт. `SetPlayer` создаёт и регистрирует тик игрока, `RegisterEnemies` — тики врагов (интервал 1, первое срабатывание в момент 1, `Owner` — боец, `isEnvironment = true`; формулы и поля — [effects.md](effects.md)). При откате: тик игрока (`Owner` — `Player`) — сторона игрока: его записи не отменяются, он сдвигается на −S, поэтому следующее затухание игрока наступает через то же число секунд по его часам; тик врага — мировой: затухания в интервале отменяются и при повторе проходят заново теми же числами, а в моменте повтора окружение всё равно идёт после новых событий.

**Оглушение игрока и снятие тиков.** Оглушение игрока (`AppliedEffectEntry.Apply` для `Stun` с целью `Player`) вызывает `AdvanceTime` внутри события врага или карты: цикл `ResolveUpTo` продолжает разбор до нового `CurrentTime`. Тик эффекта, у которого стаки дошли до 0, снимается из очереди с записью в журнал; откат возвращает его на прежнее место, а тик на игроке (сторона игрока) откатом не трогается — как и все записи с целью `Player`.

**Оглушение игрока посреди каста.** Оглушение на игроке всегда прибавляет N секунд к **текущему** времени боя, в том числе посреди каста: каст 0→5 и Оглушение 3 в момент 2 дают время 8 (решение пользователя, вариант А). `ResolveUpTo` продолжает разбор до нового времени.
